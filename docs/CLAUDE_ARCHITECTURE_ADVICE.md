# 아키텍처 리뷰: 독서모임 Flask 앱 공개 경로

표기: **[측정]**은 제공된 측정값, **[추론]**은 그 측정값에서 끌어낸 판단, **[미검증]**은 아직 확인되지 않은 가정입니다. 저는 아무것도 실행하거나 접속하지 않았으며, 브리프에 적힌 내용만 근거로 삼았습니다.

## 결론 요약

- **주 권고:** B안(기존 workers.dev Worker + 좁은 VPC Service + 사설 cloudflared)을 평가하되, Funnel 경로는 롤백용으로 그대로 둡니다.
- **A안 정적 CDN:** 지금은 보류합니다. 정적 자산 버전 관리는 곧 나올 UI 릴리스에 함께 넣습니다.
- **증설과 마이그레이션:** 서버 증설, 워커 증가, 로컬 DB 이전, 프런트 재작성은 관측된 문제와 관련이 없습니다.
- **가장 큰 실제 위험:** 속도가 아니라 **검증된 복원 절차가 없다는 점**입니다.

## 1. 타이밍이 증명하는 것과 증명하지 못하는 것

**[측정]**
- loopback 응답은 대부분 3–66ms이고, /now만 279ms입니다.
- 같은 경로의 공개 응답은 1.25–4.8초입니다. 3ms짜리 CSS도 공개 경로에서는 1.28초가 걸립니다.
- 공개 relay에서 작은 403 응답은 첫 요청 약 3.4–3.7초, 이후 0.9–1.2초입니다. tailnet 사설 경로에서는 6ms입니다.
- VM 부하는 0.00이고 재시작 기록이 없습니다.

**[추론]**
- 지연의 대부분은 앱이나 DB가 아니라 **Funnel 공개 relay 구간**에서 생깁니다. 로직이 거의 없는 403 응답만으로도 1–3.7초가 재현되기 때문입니다.
- 첫 요청이 특히 느린 것은, 장거리 relay 위에서 매 연결마다 핸드셰이크를 다시 하는 비용으로 보입니다.
- 클라이언트가 서울이 아닌 홍콩(HKG) Cloudflare에 붙는다는 점도 왕복 시간을 늘립니다. 이 부분은 어떤 안을 택해도 남습니다.

**증명하지 못하는 것**
- Cloudflare Worker가 실제로 어느 Funnel relay를 쓰는지.
- Funnel 대역폭 제한이 사진 업로드에 영향을 주는지 **[미검증]**.
- 로그인한 대시보드의 성능. 소스상 순차 DB 호출과 반복 쿼리가 있어 추가 지연이 있을 수 있지만, **측정된 적이 없습니다.**
- 3회 순차 측정이므로 p90이나 동시성 특성은 알 수 없습니다.

**다른 처방이 효과가 없는 이유**
- **VM 증설이나 Gunicorn 워커 증가:** CPU 포화 증거가 없고, loopback이 이미 빠릅니다. 효과를 기대하기 어렵습니다 **[추론]**.
- **로컬 Postgres 이전:** DB 읽기가 포함된 keep-alive도 loopback에서 66ms입니다. 1초 이상의 지연을 설명하지 못하고, 오히려 백업 책임만 집으로 옮겨옵니다. 이전할 근거가 없습니다.
- **프런트 재작성:** HTML 첫 바이트 자체가 느린 문제라서 해결되지 않습니다.
- **대시보드 쿼리:** 별도 과제입니다. 나중에 앱 내부에서 프로파일링하고 쿼리를 정리하는 것이 맞고, 인프라 문제가 아닙니다.

## 2. A / B / C 비교

### A: 현행 Funnel + 정적 CDN
- 정적 파일 요청만 빨라집니다.
- HTML, 로그인, OAuth 리다이렉트 연쇄, DB 페이지, 업로드, SSE는 전부 Funnel을 계속 지납니다.
- 결국 **증상의 일부만** 다루면서, 릴리스할 때 맞춰야 할 산출물을 하나 더 만듭니다.

### B: workers.dev Worker + VPC Service + 사설 cloudflared
장점:
- 공개 이름과 Kakao 콜백이 그대로 유지됩니다.
- 도메인 구매가 필요 없고, 원본은 공개되지 않습니다.
- cloudflared가 미리 연결을 맺어 두므로 첫 요청 핸드셰이크 비용이 줄 것으로 **기대**됩니다 **[추론, 미검증]**.

단점:
- 베타라서 가격과 API 안정성이 보장되지 않습니다.
- 실제 응답 시간은 측정해 봐야 압니다.

### C: 일반 Tunnel + 동아리 도메인
- 정식 출시(GA) 경로라 가장 "평범하고 오래 가는" 구성입니다.
- 다만 도메인 비용이 들고, 아직 승인되지 않았습니다.
- Worker를 빼면 공개 이름과 Kakao 콜백이 바뀝니다.
- 도메인 갱신은 인수인계에서 가장 놓치기 쉬운 자산입니다.

### 판단: 이 상황에서 B의 베타 위험은 감수할 만합니다
핵심 근거는, **Worker가 이미 공개 이름과 원본 전송 방식을 분리하고 있다**는 점입니다.
- VPC 바인딩이 바뀌거나 유료화되면, Worker의 원본 설정만 Funnel(또는 나중의 C)로 되돌리면 됩니다.
- 사용자에게 보이는 URL은 바뀌지 않습니다.
- 따라서 베타 위험은 "되돌릴 수 있는 위험"입니다.

C는 버리는 안이 아니라 **출구 계획**으로 남겨 둡니다. 동아리가 도메인을 소유하기로 하거나 VPC 조건이 나빠지면 그때 전환합니다.

### B에서도 바꾸지 않을 것
- origin secret 검사와 Worker의 전달 헤더 덮어쓰기는 유지합니다. cloudflared도 localhost로 접속하므로 심층 방어가 계속 필요합니다.
- 바인딩은 전체 네트워크가 아니라 127.0.0.1:5000 **단일 서비스**로만 합니다.
- Worker에 VPC 장애 시 Funnel로 자동 우회하는 기능을 넣는다면 **GET/HEAD만** 허용합니다. POST를 재시도하면 출석이나 업로드가 중복 기록될 수 있습니다.

## 3. UI 릴리스와 정적 자산 버전 관리

현재 준비된 A안의 실제 위험은 "오래된 캐시"가 아닙니다.
- `max-age=0, must-revalidate`이므로 브라우저는 매번 재검증합니다.
- 진짜 위험은 **버전 불일치**입니다. Flask 릴리스와 Worker 자산 배포가 따로 움직이면, 새 HTML에 옛 CSS가 붙거나 그 반대가 됩니다.
- 파일 이름이 고정되어 있으면 "없으면 원본으로 fallback"하는 동작이 이 불일치를 오히려 **가립니다.**

비례적인 해법은 다음과 같습니다.

1. **버전 관리는 Flask 저장소 한 곳에서 합니다.**
   - Jinja 헬퍼가 파일 내용 해시로 `/static/app_ui.<hash>.css` 같은 경로를 만들고, 원본이 그 경로를 직접 서빙하게 합니다. 해시 경로에 한해 긴 `immutable` 캐시를 줍니다.
   - HTML과 동적 응답은 no-store를 유지합니다.
   - 이렇게 하면 별도 파이프라인 없이 재방문 시 자산 비용이 사라집니다 **[추론]**.
2. **이 변경은 진행 중인 UI 세션의 릴리스에 포함합니다.** 별도 배포로 끼워 넣지 않습니다.
3. **CDN 자산은 나중에 선택 사항으로 둡니다.**
   - 해시 경로라면 CDN에 파일이 없을 때 원본 fallback이 **정확한** 파일을 줍니다.
   - 버전 불일치가 정확성 문제가 아니라 단순한 캐시 미스로 바뀝니다.
   - 그 단계에서는 Worker 자산 빌드가 같은 커밋에서 나오도록 고정하면 충분합니다.
4. **B로 전환하면 A의 이득이 줄어들 수 있습니다.** A의 필요성은 B 측정 후에 다시 판단하는 편이 합리적입니다.

## 4. 평가와 전환 게이트

아래 단계는 모두 각 시점에 승인이 필요하며, 지금 설정해도 된다고 가정하지 않습니다.

1. **비공개 측정**
   - 별도 이름의 Worker를 VPC 경로로 연결합니다.
   - 익명 GET, 정적 파일, 403 응답만 사용합니다.
   - 기존 경로와 새 경로를 **번갈아 같은 시간대에** 각 30회 이상 측정하고, 첫 요청은 따로 집계합니다.
   - 중앙값과 p90을 비교합니다.
2. **합성 진단 엔드포인트**
   - 서명된 단기 토큰으로 보호합니다.
   - 합성 SSE 스트림, 저장하지 않고 버리는 대용량 바디 수신, Set-Cookie 다중 응답, 수동 리다이렉트를 검증합니다.
   - 실제 조 편성, 출석, Storage 쓰기는 사용하지 않습니다. 실제 회원 데이터 쓰기나 POST 재생은 금지입니다.
3. **로그인 검증**
   - 스테이징 Kakao 콜백 등록(OAuth 변경이라 승인 필요)과, 본 전환 직후 즉시 롤백 가능한 상태에서의 실제 로그인 확인 중 하나를 고릅니다.
4. **전환**
   - Worker의 새 버전을 배포하는 방식으로 전환합니다.
   - Funnel은 일정 기간 켜 둡니다.
   - 롤백 = 이전 Worker 버전 재배포입니다.
5. **재부팅 시험**
   - cloudflared 자동시작까지 포함해 계획된 재부팅으로 확인합니다.

## 5. 이식성, 백업, 재부팅

**이식성 설계** (인수인계 패키지와는 구분되는, 지금 할 수 있는 설계입니다)
- systemd 유닛과 설정 템플릿은 저장소에 둡니다.
- 비밀값은 환경파일과 Cloudflare Secret에만 둡니다.
- 호스트 이전 = 새 VM + 환경 복원 + 새 cloudflared 커넥터 토큰입니다. Worker와 공개 이름은 그대로입니다.
- 데이터는 Supabase에 남으므로 **호스트 이전과 데이터 이전이 분리**됩니다.

**의존성 목록**
- Worker, Tunnel/VPC, Supabase, Kakao 앱, Tailscale을 "어떤 계정의 무엇에 의존하는지" 한 문서로 정리합니다.
- 이는 계정 이전이 아니라 설계 문서이며, 사용자가 보류한 인수인계 작업과는 별개입니다.

**백업 [측정: 아직 활성화 안 됨]**
- 오프사이트 pg_dump와 Storage 사진 백업을 활성화합니다.
- **비운영 DB로의 복원 리허설**까지 해야 백업이 있다고 말할 수 있습니다.

**재부팅 [미검증]**
- Windows 재부팅 후 복구는 아직 시험되지 않았습니다.
- BIOS의 AC 전원 복구 설정도 확인되지 않았습니다. 정전 후 누군가 전원을 눌러야 하는 구조일 수 있습니다.

## 6. 가장 중요한 우려

- **원래 아키텍처:** 성능 병목은 Funnel relay입니다. 그러나 더 심각한 것은 **복원 검증이 없는 단일 데이터 의존**입니다. 지연은 되돌릴 수 있지만 데이터 손실은 되돌릴 수 없습니다.
- **준비된 최적화(A):** 작은 쪽 문제(자산)를 고치면서, UI 변경이 진행 중인 바로 이 시점에 두 산출물의 버전 결합을 추가합니다. 게다가 고정 파일명과 fallback 조합이 그 불일치를 숨깁니다.

## 사람이 결정해야 할 것 (2가지)

1. **원본 전송 방식:** Funnel 롤백을 유지한 채 B(베타, 무료, 공개 이름 유지)를 평가할지, 아니면 지금 도메인 비용을 승인하고 C(GA)로 갈지.
2. **릴리스 주체:** 정적 자산 버전 관리를 UI 세션 릴리스에 통합하고 A안 CDN을 B 측정 이후로 미룰지, 아니면 현재 서버 리비전에 고정한 A를 먼저 배포할지.

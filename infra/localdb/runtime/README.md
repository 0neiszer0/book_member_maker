# 운영용 로컬 DB 준비

2026-10-29: 파일 준비 단계. 운영 연결은 아직 Supabase다. 기존 합성 시험·실제 백업 두 번 복원 결과는 `../RESTORE_VALIDATION.md`를 따른다.

## 고정 구성

- PostgreSQL / PostgREST / Storage API / Envoy, 시험한 것과 동일한 이미지 digest.
- 메모리 합계 상한 1,248MiB. 실제 복원 당시 약184MiB 관측은 최대 부하 보증이 아니다.
- DB 포트는 발행하지 않는다. 앱용 API만 VM의 `127.0.0.1:55480`에 연결한다.
- private 설정 `/etc/bookmembers-db/database.env`, Docker named volumes. IP·개인 계정은 소스에 넣지 않는다.
- `prepare.py`는 새 설정만 생성하며 기존 디렉터리 덮어쓰기, 컨테이너 기동, 앱 전환을 하지 않는다. 서버 키 만료는 10년이며 생성·만료 시점을 PREPARED.json에 기록한다. 키는 서버 전용이며 이전/유출 시 교체한다.
- Docker가 부팅 시 시작하고 각 컨테이너가 복구된다. `bookmembers-db.service`가 상태를 기다린다. 앱과 알림 서비스에는 `app-localdb.conf`를 적용한다. API가 늦게 준비되면 앱은 기존 재시작 정책으로 재시도한다.

## 승인 후 최종 전환 순서

1. 자동 외부 백업을 설치해 실제 실행 1회와 업로드 검증을 마친다. 관리자 알림은 비밀값이 없는 상태 파일만 읽는다.
2. 이 runtime을 새 전용 볼륨으로 준비한다. 기존 시험·복원 볼륨을 운영에 재사용하지 않는다.
3. 최종 전환 승인 직후 앱·알림·위키 쓰기를 일시 정지하고 새 백업을 만든다. 직전 복원 시험 사본은 최신 운영 사본으로 간주하지 않는다.
4. 새 DB의 public이 비어 있음을 확인하고, 검증한 pg_restore 순서로 소유자·권한을 보존해 복구한다. Storage API로 버킷/파일을 복구한다. 앱 SQL 마이그레이션을 다시 모두 덮어쓰지 않는다.
5. 동결 원본과 행 수/권한/시퀀스, 버킷·파일을 대조한다. 검증된 미디어 프록시 코드와 URL/서버 키를 적용한다. 비밀 env는 root 전용으로 유지한다.
6. 백업 설정도 같은 로컬 DB 및 파일 API로 바꾸며, DB client는 해당 컨테이너의 loopback network를 쓴다. database.env도 암호화 백업에 포함한다.
7. 내부에서 준비 여부·anon 거부·회원 읽기를 확인한 뒤 앱/위키/알림을 재개한다. Worker·Render·Kakao·GitHub main 변경은 없다.
8. 회원 쓰기 재개 전 실패하면 이전 앱 설정으로 복귀한다. 쓰기 재개 후에는 새 로컬 기록 보존을 우선하며 Supabase로 자동 복귀하지 않는다.
9. 별도 재부팅 승인 후 Windows→VM→DB/API→앱/위키/알림/Tunnel→사이트를 실제 확인한다. Supabase 삭제/해지는 이 전환에 포함되지 않는다.

현재 이 순서는 전환 실행 기록이 아니다. 실행 단계마다 상위 outputs 상태 파일을 갱신한다.
